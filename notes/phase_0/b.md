# Phase 0 — Interview Notes

## CMake, Build Tools, Generators & Compilers

---

# Q1. "Are you using CMake? If not, what are you using instead?"

### Answer

> **We are still using CMake. CMake is our build-system generator, but CMake itself is not the tool that actually compiles the code. In our Windows MinGW environment, we are using the MinGW Makefiles generator, which generates a Makefile that is executed by `mingw32-make`. `mingw32-make` then invokes the GCC/G++ compiler and linker to produce the final executable.**

### Short version

> **CMake → MinGW Makefiles → mingw32-make → G++ → executable**

This distinction is very important.

We are **not replacing CMake with `mingw32-make`**.

They have different jobs.

---

# Q2. "Then what exactly is CMake?"

### Answer

> **CMake is a cross-platform build-system generator. We describe our project and its build requirements in `CMakeLists.txt`. CMake reads that configuration and generates build files for a particular build system.**

For our current Windows setup:

```text
CMakeLists.txt
      ↓
    CMake
      ↓
MinGW Makefiles
      ↓
mingw32-make
      ↓
     G++
      ↓
   Linker
      ↓
 reclaim.exe
```

---

# Q3. "What is a CMake generator?"

### Answer

> **A CMake generator determines what build system CMake will generate.**

Examples include:

```text
MinGW Makefiles
Unix Makefiles
Ninja
Visual Studio
```

For our project on Windows, we're currently using:

```text
MinGW Makefiles
```

So when we execute:

```bash
cmake -G "MinGW Makefiles" ..
```

we are telling CMake:

> Generate a build system that can be built using MinGW's `mingw32-make`.

---

# Q4. "What is `mingw32-make` then?"

### Answer

> **`mingw32-make` is a build tool. It reads the Makefile generated by CMake and executes the compilation and linking commands necessary to build the project.**

So:

```text
CMake
```

generates the instructions.

```text
mingw32-make
```

executes those instructions.

---

# Q5. "Is `mingw32-make` a compiler?"

### Answer

> **No. `mingw32-make` is a build tool, not a C++ compiler. It determines which files need to be rebuilt and invokes the compiler and linker commands specified by the generated Makefile.**

Our compiler is:

```text
GCC/G++
```

---

# Q6. "What is G++?"

### Answer

> **G++ is the GNU C++ compiler driver. It compiles our C++ source code into object files and also invokes the linker to produce the final executable when required.**

Conceptually:

```text
main.cpp
   ↓
  G++
   ↓
main.o
   ↓
Linker
   ↓
reclaim.exe
```

---

# Q7. "Why don't you just use G++ directly?"

This is a very good interview question.

### Answer

For a tiny project, we could:

```bash
g++ main.cpp -o reclaim
```

But as the project grows, we'd have to manually manage:

* source files
* header directories
* libraries
* compiler flags
* linker flags
* Debug/Release configurations
* platform differences
* dependencies
* tests
* build configurations

CMake lets us describe these requirements once:

```text
CMakeLists.txt
       ↓
CMake
       ↓
platform-specific build system
       ↓
compiler/linker
```

So:

> **G++ performs compilation, while CMake manages the project build configuration.**

---

# Q8. "Why did you choose MinGW Makefiles?"

### Answer

> **Because our current Windows development environment uses the MinGW-w64 toolchain. The MinGW Makefiles generator allows CMake to generate Makefiles compatible with the MinGW build tools, which then invoke GCC/G++ to build our C++ project.**

Our current environment is essentially:

```text
Windows
   ↓
MSYS2 / MinGW-w64
   ↓
GCC/G++
   +
mingw32-make
   ↓
CMake
```

---

# Q9. "Could you use another generator?"

### Answer

**Yes.**

CMake supports different generators.

For example, on Windows we could use:

```text
Visual Studio
```

and then the build chain would look more like:

```text
CMake
   ↓
Visual Studio project files
   ↓
MSVC build tools
   ↓
MSVC compiler/linker
   ↓
reclaim.exe
```

Or we could use:

```text
Ninja
```

giving:

```text
CMake
   ↓
Ninja build files
   ↓
Ninja
   ↓
G++
   ↓
reclaim.exe
```

The important idea is:

> **CMake provides a common project configuration while the generator determines which build system is used on a particular environment.**

---

# Q10. "So why use CMake at all if you still need another build tool?"

### Strong interview answer

> **Because CMake provides a platform-independent way of describing the build. The actual build tool can vary by platform or development environment. CMake abstracts that part of the process. For example, the same `CMakeLists.txt` can generate MinGW Makefiles on one environment, Visual Studio project files on another, or Ninja files on another.**

This is one of the main reasons CMake is useful for cross-platform C++ projects.

---

# Q11. "Explain your entire build process."

This is the answer I especially want you to memorize.

> **First, I define the project in `CMakeLists.txt`. CMake reads that configuration and generates a build system using a selected generator. In our current Windows environment, we're using the MinGW Makefiles generator. That generates a Makefile. `mingw32-make` reads that Makefile and determines what needs to be rebuilt. It invokes G++ to compile the C++ source files into object files, and the linker then combines the required object files and libraries into the final executable, `reclaim.exe`.**

### Diagram

```text
                 CMakeLists.txt
                       │
                       ▼
                     CMake
                       │
                 CMake Generator
                       │
                       ▼
              MinGW Makefiles
                       │
                       ▼
                 mingw32-make
                       │
                       ▼
                     G++
                       │
                       ▼
                 Object files
                       │
                       ▼
                    Linker
                       │
                       ▼
                  reclaim.exe
```

# Q12. "What happened when you got the `nmake` error?"

This is actually a great interview story because you encountered a real build problem.

### Answer

> **The build directory had previously been configured with the NMake Makefiles generator. When I ran `cmake --build .`, CMake tried to invoke `nmake`. However, my current environment was MinGW/MSYS2 and didn't have `nmake` available. I deleted the old build directory to remove the previous CMake configuration and regenerated it using the MinGW Makefiles generator.**

Then:

```bash
cmake -G "MinGW Makefiles" ..
cmake --build .
```

gave us the correct build chain.

---

# Q13. "Why did you delete the build folder?"

### Answer

> **CMake stores configuration information in the build directory, including the selected generator. Since the existing build directory had been configured for NMake, I removed it and configured a fresh build directory for MinGW Makefiles.**

This is a very practical CMake answer.

# ⚠️ One wording mistake to avoid in the interview

Don't say:

> "CMake compiles my code."

Say:

> **"CMake generates the build system, which then invokes the compiler and linker."**

Also don't say:

> "We're using mingw32-make instead of CMake."

Say:

> **"We're using CMake with the MinGW Makefiles generator, and `mingw32-make` is the build tool executing the generated Makefile."**

That distinction shows that you actually understand the build system rather than just memorizing commands.
